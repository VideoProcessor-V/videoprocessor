## Should fix
3. **[bb461843] Old `mode: listen` files now relay.**
   - `listenRelay` defaults to true (LedDriveConfig.h:211). The legacy path of `ApplyCommandSource` does
     not touch it, so a file with only `mode: listen` and a `listen_script` now has VP open the projector
     port and relay, where before the script drove COM1.
   - The prompt's rule is that a mode-only file must behave exactly as before.
   - An existing deployment keeps its old `scripts\main_vp.py` (the seed is `onlyifdoesntexist`). Its
     `> com1` writes then fail ("Access is denied" in led-script.log once per command), while VP relays its
     notifications.
   - Fix: legacy listen (no `command_source`) keeps `listenRelay = false`.
4. **[bb461843] The relay forwards datagrams from any local program while VP's script runs.**
   - `Receive` has no sender check (ScriptListener.cpp:114-150). The relay checks only the value range
     and that the script is Running (LedDriveModule.cpp:1093).
   - Scenario: a second, hand-started main_vp.py. Its COM1 writes fail, but its notifications are relayed,
     so the projector gets two scripts' commands interleaved.
   - docs/VP-led-core-sources.md:45 says anything else reaching the port "is logged and refused". That is
     true only while VP's script is *not* running. The doc should say so; Config says nothing.
   - The refusal is logged once per message with no rate limit, so a noisy local sender can flood vp.log.
5. **[bb461843] The relayed script can be started blind.**
   - `scriptHost.Update(…, relay)` starts the script with `VP_LED_RELAY=1` (it echoes to nul) before and
     regardless of the listener opening (LedDriveModule.cpp:1007-1041).
   - `main_vp.py` hard-codes UDP 47811 (main_vp.py:39).
   - Scenario: 47811 taken, or `listen_port` set to another value. The script writes nothing, VP hears
     nothing, and the projector is never driven. The only sign is "waiting for the script's first command"
     in the log.
   - Fix: relay only while the listener is open, and warn when `listen_port` ≠ 47811.
6. **[bb461843] The listen CSV can grow without bound if rotation fails.**
   - The `MoveFileExA` result is ignored (LedDriveModule.cpp:1061, ScriptListener.cpp:185).
   - If a log tailer holds the file without delete sharing, the rename fails, the reopened size is still
     over the cap, and every tick closes, retries, reopens and appends "# continued".
7. **[bb461843] "TICK only on agreement change" writes nearly every tick.** The change key is built
   from the raw targets (tp / lightTarget, tc / contrastTarget; LedDriveModule.cpp:1163-1167), not the
   agreement, so moving content writes a row almost every tick. It is bounded by the 8 MB cap, but not
   what the doc (VP-led-core-sources.md:59-60) says. Key on the differences or on agree/disagree.
8. **[bb461843, Config] The adaptive gamma box does not show what an old file does.**
   - For a mode-only file, the runtime keeps `adaptiveGamma = true` in every mode (struct default; shadow
     lift = `shadow_lift_ansi`).
   - The box shows "on" only for compensate or `script_smoothing: true`. For an old picture_only, listen,
     script or log_only file with `shadow_lift_ansi > 0`, the box says off while the lift is on.
   - The first change of source then writes `adaptive_gamma: false` from the box, and silently ends the
     lift. For an old `picture_only` file this also ends the picture terms, which were its whole purpose.
   - Default `shadow_lift_ansi` is 0, so most files are unaffected.
9. **[5b2c4470, item 5 partly] picture_only right after a live switch from listen.** `Reconfigure`
   does not clear `smoothing`, so `BeginFrame` keeps applying the smoother's gain until the thread's next
   pass. That is now about 50 ms instead of up to 5 s, but not "exactly 1". Clear `smoothing` and the gain
   in `Reconfigure`.
10. **[merge] The displacement texture leaks.** `Warp::~Warp` (RenderedWarp.cpp:339-345) destroys
    `warped` and the dispatch but not `displacement` (RenderedWarp.h:123). `ReleaseDejudder` resets the
    warp, so each release or device change with D2 active leaks one output-size texture. It also outlives
    its device.
11. **[merge, D3 test-only] R-B on B has the wrong sign when a camera vector exists.**
    - DejudderWarp.cpp:1717-1719 and 1783-1785 apply `object_scale(vb)`, which uses A→B's camera `vg`,
      to `vb`, which is B→A (≈ −vg).
    - A pure pan with object_strength 0.5 leaves B unmoved, so blending it gives a double image.
    - Use `vb = -object_scale(-vb)`. Only with blendFrames on (off by default).

## Notes
- [D2]
  - The displacement is "displacement at the current shift × (shift − previousShift)/shift", a linear
    approximation of the step; with M6 the weight and the fixed-point vector are not linear in shift.
  - D2 covers the rendered warp only. On the source warp path the block VPVEC is still used, so the
    known gap remains there.
  - The quantizer always binds VPPIX, so the shader text changed even with D2 off. The results are
    unchanged (it is read only when `vector_pixel` > 0.5).
- [D3] Implemented in the source warp only. The planner said rendered warp only (overnight answers
  59-60), so with the rendered warp active, blendFrames has no effect. B's pixel mask always uses
  PIXEL_TRUSTED_VECTORS, while B's warp follows A's setting. In `object_scale`, R-B is applied after the
  fixed-point lookups (minor).
- [relay] If the port is busy at start, the session stays in the original listen mode until a settings
  change; it does not retry.
- [relay] An old main_vp.py without `_vp_com1` works, but logs "Access is denied" per command; there is
  no runtime warning.
- [relay] A lost loopback datagram is a lost projector command, and nothing detects it (unlikely).
- [log]
  - The CSV byte counter runs about 0.7% low (text-mode CRLF); it is corrected at each reopen.
  - led-listen-now.txt is rewritten per message batch, a few times a second at about 300 bytes. That is
    negligible and unchanged.
- [listen]
  - An unparsable datagram returns `Receive` at once; this is bounded by the sender's rate.
  - The 5 s retry also resets VP's copy of the rules (harmless while closed).
  - Without a job object, a child process of the script could still block `reader.join()`.
- [look-ahead off] The custom dim never engages (`lookaheadCovers` false). Compensate only.
- ScriptHost.h:20-23 still says VP never holds the port. That is stale since the relay.
- The search-mode fade floor ("reported" last time) is still not addressed.
