## Blockers
1. [P1] **Listen mode busy-loops when the UDP port cannot be bound.**
   - LedDriveModule.cpp:968-1111. When `listener.Open()` fails, `Receive()` returns at once
     (ScriptListener.cpp:99), and the branch ends with `continue` ("the listener's wait is this
     tick's wait"). Nothing waits.
   - The next pass calls `Open()` again and logs "cannot listen" again. It also calls
     `scriptHost.Update` every pass.
   - Scenario: port 47811 is taken (a second VP, another program). The LED thread then spins at
     one full core and fills vp.log with one line per pass.
   - Fix: wait `tick_ms` after a failed open and log it once.

## Should fix
2. [P1] **R1: after a failed extra, the replacement A still uses the extra's vectors.**
   - LibplaceboVideoRenderer.cpp ~12186-12192: on the libplacebo swapchain path, a failed extra
     render is replaced by `pl_render_image(renderer, f.image, &target, &params)`.
   - The `VectorGuard` is still in scope there, so the sigma-delta keeps `vector_source = 1` and
     VPVEC bound.
   - Effect: the dither carries along `shift − previousShift` for a picture that actually moved
     back to A. That gives a wrong carry for one refresh, and its state advances.
   - Fix: reset the guard before the fallback render.
3. [P1] **Listen: turning `listen_log` on while running never opens the CSV.** The CSV is opened
   only inside the `!listener.IsOpen() || port changed` block (LedDriveModule.cpp:975-1007). A
   `listen_log` change alone is applied in place, so logging stays off until the port changes or
   VP restarts.
4. [P1] **Listen: CNTR values from any local sender are not bounded.**
   - Only `value > 0` is checked (LedDriveModule.cpp:1032). `CNTR 99999` goes into
     `smoother.Plan`.
   - With script smoothing on, the picture gain becomes `smooth/landed` (about 0.0005), a near-black
     ramp.
   - Any program on the PC can send to 127.0.0.1:47811. Clamp to the projector's CNTR range.
   - Related: the parser casts unchecked doubles to int (`max=1e30`, `nan`; ScriptListener.cpp
     ~37-41). That is undefined behaviour, and it corrupts the agreement statistics.
5. [P1] **Listen: stopping can take up to `tick_ms` (max 5 s).** `select` waits the whole tick and
   does not wake for a stop or a new setting (ScriptListener.cpp ~109). `Stop()` is called
   synchronously by the renderer. After an in-place switch from listen to picture_only, the
   smoother gain is applied until the next pass, so picture_only is briefly not exactly 1 (reported).
6. [P2] **M6 ignores delta 14 R-B (`dejudder_object_strength`).**
   - The PIXEL_TRUST branches use `field_vector_all` without the OBJECT scaling
     (DejudderWarp.cpp:1673-1695 luma, :1722-1740 chroma; RenderedWarp WARP_BODY).
   - `field_vector` applies `vg + object_strength·(v − vg)` (:1498-1515), but M6 never calls it.
   - M6 is on by default (5c936394), so `object_strength < 1` has no effect on the picture. It
     still scales the VectorField the dither uses, which widens the known D2 mismatch.
   - R-B is off by default (1.0). Apply it in the M6 branch, or document that M6 overrides it.
7. [P2] **Live changes to the motion-fix keys never reach the matcher.**
   - `RunDejudderEstimate` calls `SetSettings` only when a field in its list differs
     (LibplaceboVideoRenderer.cpp:11649-11664). The list omits `textureTolerance`, `globalTwo`,
     `regionalHold`, `cutHistogram`, the search range, `consistencyPixels`, `fadeMatch`,
     `fadeFloor`, `verifyPixels`, `verifyShare`, `pixelTrust`, `pixelTrustLo` and `pixelTrustHi`.
   - The change is fingerprinted and logged as "dejudder_motion_fixes" (:8532-8540), but the
     matcher keeps the old values until it is recreated.
   - Scenario: Config Apply or a rule switch toggling `dejudder_pixel_trust`.
8. [P2] **Estimate ahead with the source-warp extras.**
   - `EstimateAhead` sets `c.renderedWarp = activeSettings.dejudderWarpRendered` (:11697).
   - The extras use the rendered path only when the cache exists (`cached && dejudderRenderedWarp`,
     :12050). Otherwise `dejudder->Warp()` reads the matcher's *live* field, trust and mask, not
     the snapshot.
   - Case: `dejudder_warp_stage: rendered` with an NLS shader other than the bundled two (the cache
     is never armed). After the first extra, the ahead estimate has replaced the field, so extras
     2–3 of A warp with B→C's motion.
   - Fix: base `renderedWarp` on `cached != nullptr`.
9. [P2] **At 4K the fade correction does not reach the M6 mask** (lowRes `all`, the default).
   - Only the inner matcher runs `FadeMatch` (DejudderWarp.cpp ~2600). The outer `PIXEL_MASK_BODY`
     compares the outer `halfA` with the *uncorrected* outer `halfB` (~2883).
   - In a strong fade the 4K pixel weights fall towards the hold, while at 1080p they keep moving.
   - With `dejudder_low_res search` the outer gets no fade floor either (reported).
10. [P1, non-default] **Stage 11a split blocks against the H1 feather and the H3 taper.**
    - `hold_weight()` and `block_strength()` read only the parent field (DejudderWarp.cpp:1536-1550).
    - A split block's parent is untrusted by construction (`split_sad` defaults to the tolerance),
      so its trusted neighbours fade to A next to a warping split block, and taper freezes its
      sub-vectors.
    - Since 5c936394, E2 split is off and M6 bypasses feather and taper, so this shows only with
      `dejudder_est_split: on` and M6 off.
11. [P1] **H2 hysteresis state survives a live change.** `SetSettings` only assigns
    (DejudderWarp.h). `holdState` / `subHoldState` are reset only on a block-size change or a cut.
    Turning hysteresis or the split off and on can briefly warp blocks with an old scene's vectors
    (reported, plausible).
