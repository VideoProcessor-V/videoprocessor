# Motion estimation + vector store (`motion.estimation`)

Unit: **motion** | side: input | order: 50 | status: **built** | hook point: prepass

## Purpose / why

Estimate motion on the ORIGINAL frame (source raster, before re-base/repair) with the NVIDIA optical-flow engine (NVOF) seeding VP's matcher, with a time-based look-ahead, and keep ONE vectors-valid state that every consumer obeys (invalidated at cuts, drops, repeats, drift, resyncs).

## How the code works

Checked against the code 2026-10-25 (M2 pass). The estimator itself (`Dejudder::MotionWarp::Estimate` and its searches) is compiled from `src/VP-V/modules/motion/estimation/matcher/DejudderWarp.cpp`, with its class in `src/VP-V/modules/motion/estimation/matcher/DejudderWarp.h`; the renderer host (`src/VideoProcessor-Lib/vprenderer/LibplaceboVideoRenderer.cpp`) owns every instance and wires the settings, the producer and the validity state.

### Public API

- `NvOpticalFlow::Engine` (`NvOpticalFlow.h/.cpp`): wraps NVIDIA's D3D11 optical-flow interface. `Open(device, context, w, h, preset, costs)` loads `nvofapi64.dll` from System32 at run time (nothing shipped; MIT headers in `3rdparty/nvidia-optical-flow`), needs API 5.0, opens a 4 x 4 grid, both directions, optional costs. `Run(from, to, fwd, bwd, fwdCost, bwdCost, result, continuous)` takes R8_UNORM inputs and writes R16G16_SINT S10.5 vectors and R8_UINT costs; `continuous` enables the engine's temporal hints. `LastError()` gives the reason for any failure (driver missing, API too old, no engine on this GPU / busy, init or execute failed, texture not accepted).
- `MotionAhead` (`MotionAhead.h`): the look-ahead depth policy. `AheadMs(configured)` = configured frames at the 60 Hz reference (4 = 66.7 ms); `DepthAt(configured, sourceHz, general)` turns that time into whole frames at the measured rate (24/25/30p 2, 50/60p 4, 120p 8, 240p 16 = `kMaxGeneralDepth`; an unmeasured rate or `general_rate_fixes: off` keeps the configured count). `Decide(...)` gives the depth and a `Reason` (`Active`, `ShallowQueue`, `NoFramesAhead`, `Off`, `Disabled`, `LowLatency`, `NoEngine`, `NoConsumer`); `QueueFramesFor`, `PendingJobsFor`. B1 (owner 2026-11-10, doc 91 C): `LeadFor(depth, queuedAhead)` = the frames really computed ahead: every frame queued ahead (the render loop's `queuedFutureFrames`, By frames or By time), never below the depth, at most `kMaxLead` = 13 (the 16-pair P2 ring minus the 3 pairs kept behind the render); 0 while the depth is 0. The depth keeps its other readers (queue floor, engage threshold, no-pair tracker). `kMaxLead` 13 is a STRUCTURAL CAP (16 P2 ring pairs, `kP2RingPairs`, minus the 3 kept behind the render; about 217 ms at 60p) and holds even a larger depth (240p's 16 -> 13, WAIVER-B1-01): it is the ceiling for any extended look-ahead (e.g. a TD tier) at high frame rates; raising it means a bigger P2 ring (CPU pair memory, about 0.5 MB/pair at 1080p, 2 MB at 4K).
- `MotionAhead::Producer` (`MotionAheadProducer.h/.cpp`): `Start(renderDevice, preset)`, `Stop`, `Submit(sequence, generation, luma, breakBefore)`, `SetSlot` (the P2 slot it publishes into), `Take(from, to)` / `Prune` / `StoreStats` (reads of that slot, for a standalone producer; the engine's consumers use `P2View`), `SetTargetSize`, `SetDepth`, `SetLead` (B1: the pending capacity follows max(depth, lead)), `SetGeneralRates`, `Running`, `EngineReady`, `Error`, `GetStats`, `StoreStats`. Helpers: `HalfLuma8` (half-size 8-bit luma from P010/P210, v210, UYVY/HDYC, R12B, R12L, r210/R10b/R10l, BGRA/ARGB, else the source's sampler), `FlowGlobal` (whole-frame motion and a second layer from one field, in the matcher's D1 format), `FlowExtras` (cost weights and forward/backward error per block).
- `VectorStore<Payload>` (`VectorStore.h`): pairs `(from, to)` keyed under a continuity generation; `SetGeneration` clears, `Put` refuses a stale generation, `Get` counts hits/misses, `Prune`, `Plan`; bounded, oldest first out. Its one instantiation for the P2 product is `VpMotion::P2Slot` (`VectorProducts.h`, capacity 16, owned by `VectorEngineState::p2Slot`); the readers hold a `P2View` (`VectorEngineState::P2()`).
- `OpticalFlowTrust` (`OpticalFlowTrust.h`): pure CPU maths. `CostStatistics`/`CostWeights` (cost against the field's median and MAD), `FbError`/`FbWeights` (the engine's own forward/backward consistency), `Combine`, `GlobalUsable` (ambiguity < 0.9).
- `MotionValidity::State` / `ConsumerGate` (`MotionValidity.h`): one epoch counter moved by `Invalidate(Cause)` (11 causes: resync, queue reset, gap, cadence repeat, drift drop, smooth-motion mix, re-base change, source format change, seek, motion source change, settings change); `PairValid`, `NoteKept` (the drop safety net), `KeptPairValid`, `StreamGeneration` (moves only on resync, queue reset, seek, format change), `Consume` (what changed since the consumer last looked, and whether GPU resources must be released). Consumers bind derived state with `ConsumerGate::Bind` and check it before each use.
- Resync-driven mode (Q2, inert until the renderer binds it): `MotionValidity::State::Bind/Unbind/Driven`, `PairValidAt(a, b)` (adjacent and the Indicator stamps agree on full, continuity and settings[motion]), `StreamGenerationAt(seq)` (= `Drive::FullKey`), `OnSealedChange(change, fullCause, continuityCause)`. Bound, request-time resync / queue reset / seek / format-change invalidations are only counted (`DeferredToSeal()`), settings-like causes write `settings[motion]` for the first unsealed frame (`SettingsAdvances()`), and the epoch moves when the `motion-history` reader fires at the seal of the carrying frame; Gap and the other hole causes stay immediate. `MotionResyncReaders.h` (`VpMotionResync::RegisterOn(indicator, state, readers)`) registers `motion-history` (moves the epoch; `TakeHistory()` gives forget-all, forget-re-based-holders-only and release flags) and `vector-producer` (re-keys the engage generation to the full key and records the in-flight generation to drop, with no restart: `RestartsAvoided`, `InFlightDrops`; a continuity change only notes "skip spanning pairs"). `VectorStoreKey(indicator, seq)` (`VectorStore.h`) packs era, continuity and full counts into one collision-free-within-limits word. No private frame history was added: every validity answer is derived from the Indicator's `StampOf`. Tests: `tests/MotionValidityResyncTests.cpp`.
- Stream-generation check of the P2 pairs (W1-C2a-F): `MotionValidity::State::SpanStatus(a, b, acrossLoss)` answers `Unknown` (unbound, or no Indicator), `Invalid` (a FULL, a continuity change or a settings[motion] advance lies in (a, b]; `acrossLoss` leaves continuity out for the gap-fill pair) or `Valid`. `StampsAgree(a, b)` == (`SpanStatus` == `Valid`): unbound it is false (the stamps never vouch for a span they did not see); it has NO production caller and is kept as a test / diagnostic API. The refusing gates (`PairValidAt`, the gap-fill pair) use `SpanStatus != Invalid`, so `Unknown` refuses nothing. `PairGenerationCurrent(g)`: a stored pair keyed with `g` belongs to the current `StreamGeneration()` (a slot never keyed by a producer, generation 0, counts as the initial generation, so it is refused after any resync / seek / queue reset / format change). Every P2 reader goes through it: `VectorEngine::FlowOf` and `VectorEngineState::FindCurrent` (ServeStatistics forward/backward, the render-time estimate) and `SharedMotionSource::Take`. In the window after a stream restart and before the producer's asynchronous `SetGeneration` re-keys the slot, a pair finished under the old key is refused; `FlowOf` counts the refusal in `FlowReadCounters::invalidated` (logged with the flow reads), `SharedMotionSource` in its `stale` count. Expectation changes under WAIVER-C2AF-01: `MotionValidityResyncTests.cpp` (unbound `StampsAgree` IsTrue -> IsFalse), `ResyncInjectionTests.cpp` off mode (`StampsAgree == true` -> `SpanStatus == Unknown` and `StampsAgree == false`) and the fixture re-key (`SetGeneration(StreamGeneration())` before publishing, as the producer does).
- `MotionEngineIdle::Keeper` (`MotionEngineIdle.h`): keeps the motion engine loaded and idle while hiccup repair (`interpolation_fill_gaps`) could need it; releases it under video memory pressure (allocation failure, or DXGI usage >= 95 % of budget) and keeps it again after 30 s with room under 85 %.
- Estimator entry points on `Dejudder::MotionWarp`: `Estimate(a, b, occlusionSlot, grainError)`, `SetExternalFlow(flow)` (a pair computed ahead), `OpticalFlowUsed`, `ExternalFlowUsed`, `GlobalFromEngine`, `OpticalFlowError`, `EngineInputSize`, `SearchHalvings`, `ForgetHistory`, `SetPictureArea`; outputs `Forward()`, `Backward()`, `Field()`, `FrameTrust()`, `Camera()`.

### Data flow

1. Render loop (queue walk, the `motionAheadFrames` hand-off in the host): once the producer runs and at least the depth is queued ahead ("engaged"), each queued source frame is handed to `Producer::Submit` once, with its luma source (it keeps the frame buffer alive), `MotionValidity::StreamGeneration()` and `breakBefore` (`DejudderPolicy::MotionAheadBreakBefore`: a capture gap, a film update, non-adjacent times or an untrusted DV pair).
2. Producer worker: `HalfLuma8` -> optional further halving to the matcher's engine size (`SetTargetSize`; any other size is skipped and nothing stored) -> upload to its own D3D11 device on the render adapter -> `Engine::Run` (preset Slow, both directions, costs) for each adjacent pair in the same generation -> read back -> `FlowGlobal` both directions + `FlowExtras` -> `P2Slot::Publish(previous, sequence, generation)` (the producer owns no store).
3. Render thread (`RunDejudderEstimate`): when `MotionValidity::PairValid(a, b, ...)` holds, `P2View::Find(a, b)` (the engine's P2 slot) -> `MotionWarp::SetExternalFlow`. `Estimate` then builds the half-size planes and pyramids (reusing A from the last pair's B), the picture area and the fade test, and:
   - an ahead pair of the right size goes straight into the engine output textures (no engine run), with its global motion and optional trust weights;
   - otherwise (a miss, no producer running, or `optical_flow: off`) the block searches run (the P2m path). SK-MV: the matcher opens NO optical-flow engine of its own; the producer is the one NVOF session per GPU. `MotionWarp::NoPairAhead()` says a pair was wanted and missing; a sustained run (longer than max(8, look-ahead depth + 4) estimates at the measured rate) or a sustained partial miss ratio (`NoPairTracker`) is the visible `motion` fallback entry (`FallbackCatalog::Motion`, `NoPairCause`).
   By default (seed mode) the engine's vectors stand in for the first sweep and the refinement follows; the engine's whole-frame motion replaces the global search when it is clear (`optical_flow_global`, `optical_flow_global_fallback`). Then consistency, quarter-pel, smoothing, verification, block split, frame trust and hysteresis produce `field`. At tall inputs (`dejudder_low_res`) an inner instance searches at half again and its results are scaled back.
4. Out: forward/backward block searches, the trusted `field` (+ sub-field), frame trust, camera, occlusion and grain-error textures, at the matcher's half size of the source (8 px blocks); `motion.vector_delivery` maps them to the consumers' geometry. The engine's whole-frame motion also feeds `source_resolution` auto's fast-pan switch and the motion intent.
5. Validity: `NoteKept` on every presented frame, and the host's `RequestMotionInvalidate(cause)` at resyncs, queue resets, re-base changes, settings and motion-source changes; consumers check `ConsumerGate` before using any vector-derived state.

### Threading

- Render thread: `MotionWarp::Estimate` (all GPU passes through libplacebo, plus the render-time engine on the same D3D11 immediate context after `pl_gpu_flush`), `Take`/`Prune`, the producer start/stop decision, `NoteKept`, `Consume`.
- Render loop (queue walk): `Submit` (takes the producer mutex briefly; never waits: beyond `PendingJobsFor(depth)` pending jobs the oldest is dropped). The render loop and the render pass (`RenderLocked`, `PlanProducer`) are the same OS thread; the producer's only other writer is the retirement path, after the render thread is joined. As hardening the loop still reaches the producer through one `std::atomic_load` copy per use (`CollectQueueAhead`, the walk's per-frame copy) and the writers publish it with `std::atomic_store` (`PublishProducer`) (P5a-rest; test `ProducerRaceTests`).
- Any thread: the renderer's queue events (Reset, LiveQueueReset, Gap, Discontinuity, FormatChange) reach `VectorEngineExtension::OnQueue`, which requests the invalidation of that host's engine (`VectorEngine::RequestInvalidationFor`, under the engine directory's leaf lock). GPU release: `OnLifecycle(GpuReleased)` stops that host's producer (`ReleaseProducerFor`).
- Producer worker thread: creates its own D3D11 device (so a start never stalls the render thread), runs the engine and the CPU extras; `HalfLuma8` splits rows over up to 4 short-lived threads for frames 512 lines and taller. Three consecutive failures stop it for the session (`Running()` false); exceptions are caught and counted.
- Locks: the producer's mutex (jobs, error, stats); the store's own mutex; `MotionValidity::State` is lock-free except the small kept-run mutex. `Invalidate` may be called from any thread.

### User-visible fallbacks / notices

None of this module's downgrades engages a "Fallbacks engaged" entry today; all are log-only (an ADR-0001 gap):

- NVOF unavailable or failed at render time -> block searches: logged once per motion-source change ("De-judder motion: block searches (no engine) - <reason>"). The failure is latched for that matcher instance.
- Producer did not start, or stopped after three failures in a row -> render-time estimation: logged once ("Motion ahead: the producer did not start / stopped (<reason>)"); retried only when the settings stop and start wanting it again.
- Short queue / no frames ahead / low latency: the "Motion ahead: configured, queued ahead, depth (reason)" log line.
- Low video memory: the idle engine is released and recreated later (logged).
- Estimate failed: "De-judder: motion estimate failed" (first, then every 2400); the de-judder holds that frame.
- Vectors invalid: consumers use their no-motion form until a fresh contiguous pair ("motion invalidated (cause)" in the log). By design, not a fallback.
- `FallbackCatalog::Motion` (`src/VP-V/core/FallbackCatalog.h`, tested in `FallbackCatalogTests`) produces `motion: matcher only (optical flow failed: <error>)` and `motion: no optical-flow look-ahead (producer stopped: <error>)`, but the host does not call it yet (its hunk is in `docs/design/silent-fallbacks-callsites.patch`, not applied in this tree). The listed entry `Motion: matcher only (NVOF unavailable: <reason>)` is produced by no code.

## Vector engine on demand

`VectorDemand.h` (header-only, pure, CPU-tested) decides when the Vector engine runs and which consumers it serves.
Synthesis consumers (dejudder extras, interpolator, hiccup repair, occlusion mask) keep their own policies and are never counted as served or unserved.

`Decide` rules, in order:

1. Not enabled: nothing (no status line). Slots off: "off (slot off)", nothing served or unserved.
2. No consumer wants vectors, or only synthesis consumers do: mode Off, idle.
3. Interlaced: no vectors, every wanting consumer is unserved (visible fallback).
4. libplacebo smooth motion: see the exception below.
5. Low latency with no frame ahead (queue capacity 0, e.g. a competitive queue): Backward pairs. Source statistics consumers (source monitor, intent) are served; source-field consumers (grain map, deband hold, detail pulse, entrance segment) and output dither are unserved ("needs a frame ahead").
6. Otherwise Forward (ForwardShallow in low latency with capacity of at least 1, e.g. a games queue that keeps one frame queued: it uses the frames its own queue already holds). Every wanting consumer is served; the estimate and producer run when anything is served. `EngageAhead(configured, capacity)` is max(1, min(configured, capacity)). Owner rule (2026-11-01): in low latency the vectors never ADD queue depth; they use only frames the mode already queues (nothing raises the queue target for the look-ahead).

`MotionAhead::Decide(..., backwardPairs)` gives depth 0 with reason BackwardPairs for the backward mode in low latency (engine available, consumer present); without the flag nothing changes.

DELIBERATE exception: while libplacebo smooth motion runs, source-domain analysis consumers (source field and source statistics) keep the VP vectors, and output-domain consumers (output dither) fall back visibly ("libplacebo smooth motion owns output"). This is analysis only: no VP interpolation or de-judder synthesis runs alongside smooth motion. Revert with `VectorDemand::kAnalysisUnderSmoothMotion = false`, which makes smooth motion exclusive (every consumer falls back visibly).

Fallback entries (`FallbackCatalog`): `vector_engine` (unserved consumers and why), `vector_engine_producer` (look-ahead stores nothing for this size), `vector_engine_global` (fast-pan / intent without whole-frame motion), `vector_engine_hook` (the K4 pre-estimate hook threw: those pairs estimated without camera guidance; M2 P5a-5).

### One motion-engine state (W2-C1, B9)

- Starters: only de-judder (the interpolator is in the de-judder family), hiccup repair (`interpolation_fill_gaps`) and the camera fit start the engine (`VectorDemand::StarterMask`). Every other consumer (sigma-delta / dither, grain map, deband hold, detail pulse, entrance segment, source monitor, intent, occlusion mask, texture restore, residual stabilise, temporal detail) is reuse-only: served while a starter runs this frame (`Input::starterEngaged`, set by the de-judder runner: de-judder standing with a strength above 0, interpolation, or the gap fill standalone), otherwise refused (`Decision::refused`, reason `NoStarter`, "idle (no starter)") and on its non-motion path. The occlusion mask alone starts the matcher only while served (`DejudderPolicy::Input::occlusionMaskServed`); being synthesis-domain it is never in `served`, so `Decide` puts it in `refused` / `unserved` itself when no starter runs (alone or beside other reuse-only wants; C1-4 fix: before it, the refusal never reached the de-judder runner). Owner-visible change: competitive low latency with statistics consumers only no longer starts a backward producer ("competitive = motion-free"). Likewise (coordinator 2026-11-11) no idle engine is kept or warmed for hiccup repair under the low-latency queue: the standalone gap repair never runs there (`DejudderPolicyRunner.h` `repairPossible`), so a held idle engine is released when the queue starts. While an engine exists without a starter the status names it ("loaded idle for hiccup repair (no starter runs it)" or "loaded, not running (no starter runs it)", `Input::engineLoaded*`), never "idle (no starter)".
- The camera fit reads only the optical-flow seed: with `optical_flow: off`, or while a failed producer start waits for its back-off, it does not start the engine and is named affected.
- `State()` (`MotionEngineStatus`): On / Degraded / Off, the leading reason, every reason bit, the starters and the affected consumers, derived in the same `UpdateVectorEngine` / `PlanProducer` call (render thread). Hard off: VRAM release (the idle keeper is pressured; `NoteVramRelease`, fed each decision), low latency without vectors, interlaced, smooth motion exclusive, `vector_demand` off; no starter is Off too. Degraded: NVOF unavailable (the last start failed), producer recovering, ForwardShallow, a resync window (1 s after a validity-epoch change; the first refresh seeds the epoch and opens none), producer not running yet.
- `Work()` (`MotionEngineWork`): monotonic counters: matcher creates, matcher estimates (not warm-ups), warm-ups, analysis estimates (the occlusion-mask / analysis-only estimates), producer starts, producer pairs (stopped producers' pairs kept), refused starts per consumer.
- Producer start retry: a failed start is latched; it is retried after a back-off (5 s, then 60 s; `motionProducerStartRetry`). While the back-off runs no start is tried, latch or not (`ProducerPlan::LifecycleInput::backoffActive`); a due retry (`retryDue`) starts it again. GPU release clears the latch and the back-off.
- Fallback entry "motion engine" (`FallbackCatalog::MotionEngine`, cached per state / reason / reasons / affected in `MotionEngineEntry`): engaged when the engine is off with affected consumers, or degraded for NVOF unavailable / producer recovering / low latency / resync (what runs instead: block searches without optical-flow pairs; only the frames already queued; the non-motion path until the next valid pair). Not engaged for `optical_flow: off` (a setting) or the producer's first frames.
- Test seam (rule 25): `VectorEngine::FailProducerStartsForTesting(reason)` makes every producer start fail with that reason, as NVOF does on an adapter or size it cannot serve, without a device (no CPU test can otherwise reach the NVOF-unavailable state; no environment variable or setting exists for it). Empty by default and never set by the product. Used by `tests/EngineAbsentPipelineTests.cpp`, which runs the per-frame order (PlanProducer, the demand input, UpdateVectorEngine, the de-judder decision, the estimate) for 600 frames per scenario: optical flow off, NVOF unavailable, smooth motion, competitive low latency, nothing absent; starters off = no motion work and every reuse-only want refused and named.
- VRAM: the matcher is the stepped T1 user `kUserMotionMatcher` ("motion engine matcher"), declared at its create site (`VectorEngineEstimate.inl`) and released in `ReleaseDejudder` (`PhaseTimeline.inl`).

## Optical-flow pairs on demand (W2-C5b)

- What: when the estimate finds no pair computed ahead (a look-ahead miss, or a hiccup gap pair the walk never computes), the look-ahead producer's ONE NVOF session computes that pair at render time while it is idle. No second session is opened and the producer is never started for it except by `optical_flow_on_demand=on` (below).
- Call sites (rule 32, HOOK FREEZE: no hook line of its own in Bill's files): the pair is STAGED from the existing look-ahead call `MotionAhead::CollectQueueAhead` (`MotionAheadWalk.h`, under the queue mutex: atomics and copies, no cache, P2 or producer lock; stall fix, re-check MUST 3) and POSTED from the existing `Impl::ResolveMotionEngine` call (`PhaseTimeline.inl`: after the queue block, queue mutex not held, before RenderLocked's estimate). The walk cannot see the dequeue's choice, so `StageOnDemandAtWalk` (`OnDemandIssue.h`) predicts it with the dequeue's own selection (A = the queue head, B = the next entry, or the one after a pulldown film update while interpolating; repeats, updates, generation changes and file frames shown without motion are refused), once per new A; a pair the dequeue then refuses is not claimed (counted `unclaimed`). The render sample is the walk-to-walk interval with no wait subtracted (the host's dequeue wait is not visible without a hook line), so the budget errs low. The post never decodes: it peeks both frames' cached queued-capture luma and skips the pair (counted `uncached`) when either has none. The checks run cheapest first: producer running (engine off = zero work), the setting, not covered by the walk or already in P2, a consumer read a pair recently (`idleSkips`), both frames cached. The request is queued (`VectorEngine::IssueOnDemand` -> `RequestPair`), never computed. Bill-file lines: none at the call sites; the setting is parsed inside the existing PlanProducer hook block (`pin.onDemand`).
- Fill: the estimate (`VectorEngineEstimate.inl`) claims the request for exactly its pair with `VectorEngine::OnDemandFill` before the block searches would run. A pair it serves is published as `VpMotion::Source::EngineAtRender`, shown as "optical-flow engine (computed on demand)" and noted as "engine on demand" (never as computed ahead).
- Budget: `OnDemand::RenderBudget` = source period - EWMA(measured render time) - 10% of the period; half the period until measured; 0 when the rate is unknown. The render sample is the dequeue-to-dequeue interval minus the dequeue wait and this cycle's on-demand wait.
- Four miss causes (the no-pair cause, Ctrl+I / Config status, the matcher stands in): `OnDemandLate` (not answered within the budget; abandoned, so the worker skips it before any GPU work; logged first and every 10th), `OnDemandNoBudget` (budget 0: nothing asked of the engine), `OnDemandUnavailable` (no producer, stopping, refused or failed), `OnDemandUncached` (not asked: a frame's luma was not cached at the dequeue, the usual case at depth 0 in low latency; the fill of exactly that pair reports it, never plain `Missing`).
- Setting `optical_flow_on_demand`: `auto` (default) = OFF on every profile - today's behaviour - until the owner decides from the W2-C5b measurement table (the candidate is "auto = on in standard mode"); `on` = in standard mode, and in low latency only with a queue ahead (`queueAheadCapacity >= 1`; ProducerPlan starts the producer there, look-ahead depth stays 0) - competitive (no queue ahead) stays motion-free; `off` = never asked. The renderer's PlanProducer hook block reads it no longer (rule 32): `Impl::ResolveMotionEngine` notes it each frame (`VectorEngine::NoteHostOnDemandSetting`, before RenderLocked's PlanProducer), and the engine publishes it for the walk's stage. No Config row yet (rule 32: needs a VP-V motion-rows seam or a HOOK-APPROVAL); set it in the profile.
- Measurement caveat (re-check MUST 2): `RenderSample` rejects a render interval longer than two source periods, so a loop running slower than real time (the CPU+GPU bench on a contended host) never adapts and keeps the half-period budget; the bench prints `budget_adapted` (0 = fixed half-period budget) per mode, and a table built from a 0 row does not test "period minus measured render".
- Job priority on the ONE optical-flow session (contract; TD conflict 11, refs/105 O1). Three job classes share the producer's worker: the core look-ahead pair, the on-demand request, and the long pair. Order: (1) the core look-ahead pair goes first ONLY when it is about to miss its slot (deadline slack under 2 service times); (2) otherwise the on-demand request goes first (it is for the picture on screen), with at most `kMaxRequestStreak` (2) requests in a row while a core pair waits, so the walk is never starved; (3) the long pair goes last and NEVER starts while an on-demand request waits. Built here: (2) only - requests first with the streak bound (`MotionAhead::Producer::Worker`). Not built here: the deadline test in (1) (today a core pair waits behind at most 2 requests regardless of slack) and the long-pair gate in (3) (the long-pair service `SubmitLongPair` has no such gate yet). Both are built by refs/105 (producer throughput plan) phase 1, commit "JobClass + NextJob chooser" (`enum JobClass { CorePair, OnDemand, LongPair }`, one pure chooser `NextJob(queues, now, serviceEma)` in the new `estimation/ProducerJobs.h`, tests `ProducerJobSchedulerTests`; `OnDemandEstimateTests` must stay identical). C5b does not build the chooser. The dequeue-stall fix that phase 1 also lists is already in C5b (W2-C5b 7: stage under the queue mutex, issue outside).
- Counters (`VectorEngine::OnDemandReads`): requests, served, fromSlot, late, unavailable, noBudget, gated (the C1 state gate, stubbed On until lane C1), issued, unclaimed, aheadCovered, gapServed, idleSkips, uncached, budgetMs, renderMs. Ctrl+I shows "on demand: issued N, served N, late N, no budget N, uncached N" on the de-judder's stats line while anything was issued or skipped (`OnDemandStatusSegment`).

## Contract

- Input: original frame luma at the delivered source size (before re-base/repair); queued next frames for the look-ahead
- Output: forward/backward block vectors, trusted field and frame trust at the matcher's half size of the source (8 px blocks; a further half inside at tall inputs), the engine's whole-frame motion, and the validity state
- Geometry: source raster; consumers map through motion.vector_delivery
- Delay share: 0 extra frames: motion ahead uses frames already queued (B1: every frame queued ahead, at most 13; `motion_ahead_frames` only sets the minimum, 66.7 ms as whole frames at the source rate, that the queue floor keeps)
- Look-ahead: every frame queued ahead (B1 lead, at most 13); `motion_ahead_frames` = the time-based minimum (a short queue gives fewer pairs ahead, the rest is estimated at render time)
